WebAssembly has moved well past its browser origins. It now powers serverless edge functions, plugin systems, containerless workloads, and secure multi-tenant compute platforms. If you are interviewing for a role at Cloudflare, Fastly, Fermyon, Docker, or any company building on the BytecodeAlliance stack, you will be expected to go well beyond "Wasm is fast in the browser." This guide covers the technical depth those interviews require.

## What WebAssembly Is and Why It Matters

WebAssembly (Wasm) is a portable binary instruction format designed as a compilation target. Code written in C, C++, Rust, Go, or AssemblyScript is compiled to a `.wasm` binary that any conforming runtime can execute. The original design goal was near-native performance in the browser, with a well-defined security sandbox and a deterministic execution model.

What makes Wasm durable as a technology:

- **Portability**: One binary runs on x86, ARM, RISC-V, or any architecture with a Wasm runtime. No recompilation, no ABI mismatch.
- **Performance**: Wasm is designed for efficient ahead-of-time (AOT) or just-in-time (JIT) compilation. For compute-intensive code, it approaches native speed without the attack surface of native code running outside a sandbox.
- **Beyond the browser**: The same properties that make Wasm useful in the browser — sandboxing, portability, fast startup — make it attractive for server-side plugins, edge compute, and secure multi-tenant environments.

Interviewers will test whether you understand *why* these properties matter in a production systems context, not just in theory.

## The Wasm Binary Format

A `.wasm` file is a binary-encoded module. The module is the fundamental unit of code in WebAssembly. Know these core concepts:

**Linear memory** is a flat, contiguous byte array that both the Wasm module and the host environment can read and write. It grows in 64 KB pages. This is how Wasm modules handle heap allocation — there is no garbage collector built into the Wasm spec itself. If your source language (Rust, C) has manual memory management, that logic compiles into the Wasm module. If your source language has a GC (Go, Java), the GC also compiles in, which is why Wasm binaries from GC'd languages tend to be larger.

**Tables** hold references to functions. They are used for indirect function calls — the Wasm equivalent of function pointers. They are type-checked at runtime.

**Imports and exports** define the boundary between a Wasm module and its host. A module can import functions from the host (for example, to call into JavaScript APIs in a browser, or to call WASI system calls on a server). A module can export functions, memory, and tables for the host to use.

**What Wasm is not**: Wasm modules do not have direct DOM access. In a browser, DOM manipulation requires JavaScript glue code — typically generated by tools like `wasm-bindgen`. Wasm does not inherently have POSIX I/O. There is no `open()`, `read()`, or `write()` in the Wasm spec. This is where WASI enters.

## WASI: WebAssembly System Interface

WASI is a standardized system interface for running Wasm outside the browser. It defines how a Wasm module calls into the host for file I/O, networking, clocks, random number generation, and other OS-adjacent capabilities.

WASI Preview 1 (the original version) defined a flat set of syscall-like functions. It is widely supported but limited in expressiveness and composability.

**WASI Preview 2** is the current direction. It introduces the **component model**, which is a significant architectural shift:

- Instead of raw syscall-like functions, modules expose and consume **typed interfaces** defined in **WIT** (WebAssembly Interface Types).
- WIT is an IDL (interface definition language) that describes what a component imports and exports in terms of types: records, variants, options, results, resources.
- Components can be composed: you can link a Wasm component that implements HTTP handling with a component that implements key-value storage, without either component knowing the other's source language.
- This enables a genuine module ecosystem where components are language-agnostic, versioned, and composable.

In interviews at companies working on the component model ecosystem (Fermyon, BytecodeAlliance contributors, Fastly), expect to discuss how WIT interfaces are defined, how `wit-bindgen` generates language bindings, and the difference between a Wasm module and a Wasm component.

## Compiling to Wasm

**C and C++**: Emscripten is the standard toolchain. It compiles via LLVM and generates both `.wasm` and JavaScript glue code for browser use. For WASI targets, `wasi-sdk` provides a clang-based toolchain without the JS glue.

**Rust**: The most mature Wasm ecosystem of any systems language. `wasm-pack` handles browser-oriented builds; `wasm-bindgen` generates the JS bindings. For WASI targets, compile with `--target wasm32-wasip1` or `wasm32-wasip2`. `cargo-component` handles the component model workflow. Rust-to-Wasm is the default choice when you need small binary size, no GC overhead, and predictable performance.

**Go**: Experimental WASI support exists (`GOOS=wasip1 GOARCH=wasm`). Go's GC and goroutine scheduler compile into the binary, making it larger and slower to start compared to Rust. Useful if your team is Go-first and performance constraints are moderate.

**AssemblyScript**: A TypeScript-like language that compiles directly to Wasm. Lower ceiling than Rust for systems work, but significantly lower barrier for TypeScript developers building Wasm plugins or compute modules.

The interview question "When does Rust-to-Wasm make sense over JavaScript?" has a concrete answer: when you have compute-intensive code (parsing, encoding, cryptography, simulation) where the overhead of crossing the JS/Wasm boundary is outweighed by the execution speed, or when you need to reuse existing Rust or C code in a browser or edge context.

## Edge Computing with Wasm

This is where most of the engineering hiring is concentrated right now.

**Cloudflare Workers** runs JavaScript and Wasm in V8 isolates distributed across Cloudflare's global network. Workers can import `.wasm` modules and call into them directly. Workers AI and Cloudflare's broader developer platform are built on this model.

**Fastly Compute@Edge** runs Wasm modules (primarily Rust and Go) on Fastly's edge network. Modules are compiled ahead of time at deploy, giving sub-millisecond cold starts.

**Fermyon Spin** is a WASI-native application framework. You write components in any WASI-compatible language, define triggers (HTTP, message queues), and deploy to Fermyon Cloud or a self-hosted Spin instance. It is the most component-model-forward runtime in production use.

**wasmCloud** takes a distributed actor model approach, orchestrating Wasm components across cloud and edge nodes with a capability-provider system.

Why Wasm beats containers for edge:

- **Cold start**: A Wasm module starts in microseconds. A container starts in hundreds of milliseconds to seconds.
- **Security isolation**: Each Wasm module is sandboxed by the runtime. No shared kernel surface between tenants.
- **Footprint**: A Wasm binary is typically kilobytes to low megabytes. A container image is megabytes to gigabytes.
- **Portability**: One Wasm binary runs on any runtime without recompilation. Containers require architecture-specific images.

## Security Model

Wasm's sandbox is capability-based. A module can only do what the host explicitly grants it permission to do. In WASI Preview 2, this is formalized: capabilities are passed as resources through WIT interfaces. A module cannot access the filesystem unless the host passes it a directory handle. It cannot open a network connection unless the host grants that capability.

Memory isolation is enforced at the runtime level. A Wasm module's linear memory is completely separate from other modules' memory and from the host's memory. A bug in one module cannot corrupt another module's state. This is a stronger isolation guarantee than native code or most scripting runtimes.

This is why Wasm is used as a sandboxing mechanism for plugins and untrusted code — it provides isolation without the overhead of a process boundary or virtual machine.

## Who Hires Wasm Engineers

- **Cloudflare**: Workers platform, Workers AI, Wasm-based infrastructure tooling. Expect deep questions on V8 isolates, the Workers runtime model, and performance optimization.
- **Fastly**: Compute@Edge, the Lucet and Wasmtime runtimes (Fastly is a major BytecodeAlliance contributor). Expect questions on AOT compilation and the component model.
- **Docker**: Wasm container support (`docker run --runtime=io.containerd.wasmtime.v1`). Docker is integrating Wasm as a first-class container target alongside Linux and Windows containers.
- **Fermyon**: Spin framework, Fermyon Cloud, component model tooling. Expect heavy focus on WASI Preview 2 and WIT.
- **BytecodeAlliance ecosystem**: Wasmtime, WAMR, wasm-tools contributors across multiple companies.
- **Companies migrating performance-critical browser code**: Any company with CPU-intensive browser workloads (image processing, video encoding, scientific computing, cryptography) that wants to move that logic out of JavaScript and into a compiled language.

The common thread: interviewers at these companies want to see that you understand Wasm not as an optimization trick but as a systems architecture choice with specific tradeoffs around portability, isolation, startup latency, and the current state of the tooling ecosystem.
